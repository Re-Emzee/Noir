Battery Management System Firmware
STM32U5 firmware interfacing the TI BQ76920 battery monitor via I2C, providing live cell diagnostics, fault monitoring, and CAN reporting.
STM32 • I2C • BQ76920 • CAN Bus

Overview

“Would be better to not have to swim up to the boat to push an update.” — Michael prob?

This page houses the PLRS BMS Firmware Project, responsible for communicating with the Battery Management System (BMS) and collecting real-time cell data. The firmware runs on an STM32U5xx microcontroller and uses I2C to communicate with the BQ76920 battery monitor. Diagnostics and fault events are handled by firmware and sent via CAN to the Raspberry Pi. Component overview and wiring details are documented on the BMS Research page.

Events and Alert Sequence

The BQ76920 features an ALERT pin controlled by the SYS_STAT register. This pin goes high when any monitored event occurs. Clearing the corresponding bit by writing a ‘1’ resets the alert.

AddrD7D6D5D4D3D2D1D0
0x00CC_READY—DEVICE_XOVRD_UVOVSCDOCD

D7 CC_READY

  • Triggers when a new current reading is available (every 250ms if CC_EN is set).
  • Cleared by host after reading.

D5 DEVICE_X

  • Internal fault indicator; clears all CELLBAL bits.
  • Latched high until cleared by host.

D4 OVRD_

  • Indicates external pull-up override on ALERT pin.
  • Latched high until cleared.

D3 UV

  • Undervoltage fault. Discharging disabled until cleared.

D2 OV

  • Overvoltage fault. Charging disabled until cleared.

D1/D0 SCD/OCD

  • Short-circuit or overcurrent during discharge.
  • Discharge immediately disabled upon trigger.

Cell Balancing

The PLRS pack is a 4s2p configuration, meaning four cell groups are monitored by the BMS. Due to cell mismatches over time, voltages drift — the BQ76920 performs passive balancing up to 50mA per channel.

  • Balancing only occurs during charging.
  • Adjacent cells are not balanced simultaneously.
  • Control bits are auto-cleared on DEVICE_XREADY or mode change.

Testing

Testing ensures correct register communication and fault handling, both in simulation and on hardware.

Procedure

  1. Connect I2C SDA/SCL with existing 10kΩ pull-ups.
  2. Common ground between STM and BMS.
  3. Run in debug mode; inspect struct values.
  4. Confirm BMS struct initialized properly (gain/offset validated).

STM32 and AD2

Used to monitor I2C communication and verify proper register requests. Protocol analysis performed using Analog Discovery 2.

STM32 and Arduino

Arduino-based testbench simulates the BMS by responding with known register values. Target MCU: SAMD XIAO (Arduino-compatible).

Arduino Testbench Configuration

  1. Setup pull-ups and I2C pins.
  2. Common ground connection.
  3. Run and monitor serial output.

Debugging

  • Arduino logs I2C requests to serial monitor.
  • AD2 can decode I2C transactions.
  • CubeIDE debugging via sprintf() logging buffer.

Development Notes

  • Ensure I2C timing matches 400kHz mode.
  • ALERT pin must be configured with external pull-up.
  • Clear SYS_STAT bits after each event to reset ALERT line.
  • Check DEVICE_XREADY before enabling cell balancing.

PLRS STM32U5 Bootloader
A reliable dual-bank bootloader enabling remote firmware updates via CAN FD with CRC validation, flash integrity checks, and rollback protection
STM32U575 • CAN FD • Flash Memory • Embedded C • Bootloader

Overview

This project implements a robust bootloader architecture for STM32U5-based embedded systems. It enables firmware updates to be received remotely via CAN FD, validated using CRC, and safely flashed into a dual-bank memory layout with rollback capability. The system guarantees that incomplete or corrupted updates never overwrite the running application.

Key Features

  • Dual-bank flash update system with rollback safety.
  • CRC-based integrity verification before execution.
  • Remote update capability via custom CAN FD protocol.
  • Independent flash management and CAN utilities.
  • Safe transition between bootloader and application.

Architecture

The flash memory is divided into two main banks:

  • Bank 1: Contains the bootloader (first 64KB) and a buffer region for new firmware.
  • Bank 2: Contains the currently active application.

On startup, the bootloader checks a boot flag in flash memory. If set, it copies the new firmware from Bank 1 to Bank 2, performs CRC verification, and jumps to the application. If validation fails, it reverts to the existing program.

Update Flow

  1. Application receives firmware packets over CAN FD.
  2. Packets are written to Bank 1 using Flash_Write() (16-byte aligned).
  3. After transmission, CRC is computed and verified.
  4. If valid, the application sets a boot flag and triggers a system reset.
  5. The bootloader detects the flag, copies firmware to Bank 2, and clears the flag.

// Check for boot flag and perform update if needed
if (BootFlag_IsSet()) {
    if (Verify_CRC(BANK1_START, BANK1_END)) {
        Flash_Copy(BANK1_APP_START, BANK2_APP_START, APP_SIZE);
        BootFlag_Clear();
    }
}

🛰️ SpaceDance — ML Motion Tracking Game
A gesture-based rhythm game that uses real-time body tracking and motion detection to control gameplay. Built with Python and MediaPipe, SpaceDance detects poses from a webcam feed to match dance moves to beat-synchronized targets on screen. Players “dance” to hit cues, earning points for accuracy and timing.
Python • OpenCV • MediaPipe • Machine Learning • Game Design

Overview

SpaceDance combines computer vision, audio synchronization, and interactive gameplay to create an ML-powered rhythm experience. Using MediaPipe Pose for skeleton tracking and OpenCV for camera input, player motion is analyzed in real time. Each detected pose is matched to predefined motion patterns corresponding to in-game dance moves.

How It Works

  • Pose Estimation: MediaPipe extracts body keypoints (arms, torso, legs).
  • Motion Classification: Detected poses are compared to trained patterns using vector similarity.
  • Game Logic: The player’s accuracy determines scoring and combo streaks.
  • Audio Sync: Beats are time-aligned using a Python-based rhythm tracker.

Development Notes

  • Gesture recognition fine-tuned with cosine similarity of joint vectors.
  • Dynamic difficulty scaling based on player performance.
  • Optimized frame rate using multi-threaded camera capture.
  • Audio-beat detection tested with FFT-based onset detection.

🥗 MealPrep — Nutrition Tracking App
A full-stack nutrition tracker that helps users plan meals, analyze macronutrients, and visualize progress through an interactive dashboard. Built with React, Flask, and MongoDB for real-time meal data logging and personalized recommendations.
React • Flask • MongoDB • REST API • Data Visualization

Overview

MealPrep is a cross-platform nutrition management web app designed to simplify daily meal tracking and provide clear insights into dietary habits. It allows users to log ingredients, analyze their nutritional breakdown, and receive feedback on caloric balance and macronutrient targets.

Key Features

  • Real-Time Nutrition Analysis: Calculates calories, protein, carbs, and fats per meal using live food databases.
  • Custom Meal Plans: Create and store reusable meal presets for faster tracking.
  • Data Visualization: Interactive charts display nutrient ratios and weekly calorie trends.
  • RESTful API: Flask backend handles CRUD operations and authentication tokens securely.
  • Responsive UI: Built with React for a smooth and adaptive user experience.

Architecture

The application follows a clean MVC-style separation:

  • Frontend: React components for meal logging, charts, and authentication.
  • Backend: Flask REST API providing endpoints for user management, meal data, and analytics.
  • Database: MongoDB stores user profiles, meal entries, and nutrient data with flexible schema design.

Example Workflow

  1. User logs in and records a meal (e.g., chicken salad).
  2. Frontend sends meal data to Flask API via POST request.
  3. API fetches nutrition info using an external food database and stores results in MongoDB.
  4. Frontend charts automatically update to reflect the new totals.

Development Notes

  • Authentication handled with JWT tokens and bcrypt password hashing.
  • State management via React Context API for meal data and session state.
  • Backend supports modular routes and scalable database integration.
  • Custom hooks manage user inputs and validation logic cleanly.
